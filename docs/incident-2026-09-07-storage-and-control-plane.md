Все времена ниже указаны в UTC; время Саратова — UTC+4.

## Результат и границы доказательств

- Оба диска восстановлены повторным подключением существующих томов. Новые диски не создавались, существующие диски и PVC не удалялись, форматирование не выполнялось.
- Сбой дисков локализован на уровне блочного ввода-вывода виртуальных устройств. Точную причину отказа на стороне гипервизора/хранилища по гостевым журналам установить нельзя.
- Отказы Argo CD не объясняются постоянно отсутствующими правами: его ClusterRole разрешает все операции над ресурсами, привязка к ServiceAccount корректна. Проверки `can-i watch` проходят.
- Подтверждены повторные перебои управляющего API, включая наблюдавшийся во время расследования перезапуск `kube-apiserver`.
- На управляющем узле подтверждены срабатывания OOM-killer. Нехватка памяти — основная гипотеза причины перезапусков API. Для доказательства связи конкретного перезапуска с OOM нужен журнал ядра master-ноды у Timeweb; такого журнала в нашем распоряжении нет.
- Владелец решил сохранить текущий тариф master-ноды. Подготовленное повышение в OpenTofu отменено; увеличение ресурсов не выполнялось. Правила доступа Argo CD не изменялись.

## Почему тома не восстановились автоматически

Устройства не исчезли: контрольная плоскость Timeweb и Kubernetes считали их подключёнными, но гостевой блочный ввод-вывод возвращал ошибки. Повторный `NodeStageVolume` пытался смонтировать то же неисправное устройство. Он не заменяет цикл `ControllerUnpublishVolume` / `ControllerPublishVolume`.

Установленный CSI health monitor получает список подключений; в проверенном ответе драйвера отсутствовало состояние здоровья, отражающее эти ошибки гостевого I/O. Перезагрузка worker сама по себе не гарантирует пересоздание подключения диска у гипервизора. У worker `.12` ошибки начались ещё до перезапуска, поэтому сводить оба отказа к перезагрузке неверно.

Автоматическое принудительное отключение диска по ошибке mount не включено. Для безопасного восстановления нужны: подтверждённый отказ I/O конкретного тома, остановка потребителя и подтверждение отсутствия записи на прежнем узле, обычное отсоединение с ожиданием состояния провайдера, повторное подключение, проверка прежней файловой системы без форматирования, затем запуск приложения. При недоступном узле необходим fencing со стороны провайдера. Одних прав Kubernetes и удаления VolumeAttachment для этого недостаточно.

Текущие драйвер и настройки не дают подтверждённого безопасного переключателя «перепривязывать при I/O error». Исправление механизма восстановления требует участия Timeweb либо отдельной реализации с проверенной остановкой записи; массовый автоматический detach может повредить данные.

## Мониторинг без изменения тарифа

Preset остаётся **1673**, увеличение ресурсов и OpenTofu apply не выполняются.

В Helm chart добавлены:

- Сбор Node Exporter master через приватный DNS `local-k8s-ax71701-1091532.twc1.net:9100` и метрик API через `kubernetes.default.svc:443` с проверкой TLS и существующим ServiceAccount.
- Master в общем дашборде Infrastructure Nodes и отдельный Kubernetes Control Plane: память ОС и API, CPU, диск, OOM, перезапуски, запросы и задержки API, количество объектов, логи провайдера.
- Оповещения о недоступности master/API, новом OOM, перезапуске API и остановке сбора логов. Общие пороги CPU/RAM/диска включают master.

- Сбор доступных Timeweb журналов k0s, cloud-controller-manager, healer и scaler через API. Сборщик работает на worker, использует отдельный Secret и не управляет дисками или облачными ресурсами. Токен хранится в `secret/core-platform/observability-timeweb-logs`, поле `TIMEWEB_TOKEN`; значение не хранится в Git. При ротации нужно обновить этот путь в OpenBao.

Все master-оповещения направляются в тему `core-platform`, включая остановку сбора журналов. Для CPU/RAM/диска используются существующие HostHighCpu/HostHighMemory/HostFilesystemHighUsage без второго набора правил. OOM имеет приоритет над отдельным сигналом перезапуска API: оба используют одинаковое окно 10 минут, и при приросте OOM правило перезапуска не выдаёт дополнительный метрический alert. Журналы master проходят через существующий общий pipeline gateway; второго опроса тех же записей для Telegram нет. Одинаковые ошибки объединяются в рамках минутного окна по fingerprint, как у других источников. Ошибки разных компонентов и повторение ошибки в следующую минуту не считаются одной и той же записью.

Сбор логов опрашивает четыре источника раз в минуту с перекрытием 120 секунд. Позиция сохраняется в ConfigMap после приёма OTLP; GitOps сохраняет её при синхронизации. При сбое между доставкой и сохранением возможен повтор отдельных записей. Первичная загрузка ограничена последними пятью минутами, запросы восстановления — доступной у Timeweb неделей; слишком большой backlog останавливает продвижение позиции и вызывает alert о задержке сбора. Старые журналы задним числом в общие алерты не загружаются. Журнал ядра master API провайдера не предоставляет, поэтому сопоставление OOM и перезапуска по новым метрикам усиливает диагностику, но не заменяет kernel log с именем убитого процесса.

Spans ОС не создаются. Трассировка Kubernetes API возможна только при настройке самого API-сервера владельцем managed control plane; эти параметры у нас не доступны. Приложения на workers по-прежнему отправляют собственные трассы в существующий стек.

Проверки: `python3 -B -m unittest discover -s tests`, `helm lint kubernetes/charts/core-platform-workloads`, `helm template platform-workloads kubernetes/charts/core-platform-workloads`, `kubectl kustomize kubernetes/apps`. После выкладки проверить `up{service_name=~"timeweb-kubernetes-.*"}`, метрику `timeweb_control_plane_logs_last_success_timestamp_seconds` и логи с `log.source=timeweb-api` в Grafana. Накопленный `node_vmstat_oom_kill` сам по себе не должен запускать alert: правило использует прирост.

Проверено в работающем кластере: оба master scrape target возвращают `up=1`, дашборд содержит 15 панелей, в VictoriaLogs поступили записи всех четырёх источников, сохранены четыре позиции чтения, счётчик ошибок сборщика равен нулю. SonarQube и Alertmanager остаются Ready с прежними PVC. При выкладке исправлено представление cluster ID в Helm: переменная окружения должна содержать десятичное целое, а не scientific notation; этот контракт дополнительно проверяется в CI на готовом манифесте.
